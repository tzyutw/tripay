# Tripay 歷史 Excel 重謄與結算驗證（Loop Engineering 任務）

> 給終端機 Claude Code 的完整任務指令。工作目錄：本專案根目錄。
> 執行模式：自主迴圈跑到停止條件達成才回報，中途不找 Rozi（例外見「唯二人工核對點」）。

## 目標與停止條件

把 `歷史資料匯入/excel/` 下四份 Excel 的消費，逐筆經由**真實 UI**謄入線上 Tripay（https://tzyutw.github.io/tripay/），每份 Excel 建一個新行程。任務完成的定義是四個行程**同時**滿足兩項驗收基準：

1. **每人分擔總額**：Tripay 中每位成員的應分攤總額，與 Excel 基準誤差每人 ≤ ±1（以比對幣別計；台幣比台幣、日幣比日幣）。
2. **每人結算淨額**：Tripay 結算的每人淨額（net balance，誰是債主誰欠錢、各多少），與 Excel「給X」欠款欄推得的每人淨額誤差 ≤ ±1。轉帳「路徑」（誰轉給誰）因 Minimum Transactions 可與 Excel 不同，一律以**每人淨額**為準，不比路徑。

4 行程 × 2 基準全部通過 → 產出完成報告並更新 `專案狀態.md`，任務才算結束。任何一項沒過就繼續迴圈：定位原因 → 修 → 再驗。

## Stage 0：建立驗收基準（ground truth，先於一切謄入）

寫解析腳本（Node + SheetJS 或 Python + openpyxl，**讀計算後的值** data_only）解析四份 xlsx，每檔產出 `歷史資料匯入/fixtures/<行程>.json`，內容：

- 行程：名稱、幣別、起訖日期、成員清單（含 emoji）
- 逐筆消費：title、expense_date、分類、外幣金額／台幣金額、payment_method、付款人、expense_type、splits、settled_on_spot、當日匯率
- 基準 A：每人分擔總額；基準 B：每人淨額

**解析正確性的鐵律**：腳本算出的合計必須對上 Excel 自己的「小計／總計」列（例如福岡檔 E98/F98/G98）。對不上＝解析有錯，修解析，**嚴禁手調數字讓它對上**。

## 謄入對應規則（在濟州島規則之上，用新能力取代舊迂迴）

| Excel 情況 | Tripay 謄法 |
|-----------|------------|
| 共同消費、「給X」欄**無**值（當場現金分掉/各刷各的） | `shared` ＋ **settled_on_spot=true**。付款人形式上選 Ziyu 即可（不進結算，不影響數字）。⚠️ 取代濟州島當時的 personal 迂迴——這次正是要驗證新模型能直接對上 Excel。 |
| 共同消費、「給X」欄**有**值 | `shared`、付款人＝該「給X」的 X（實際代墊人）、參與人均分。 |
| 「分開結算」區 | `individual`、付款人＝備註 emoji 指定者、各人金額＝其欠款額、付款人自己＝總額−其他人合計。 |
| A 欄為成員 emoji（個人購物） | `personal`（自付），該成員本人付。 |
| 福岡檔「均付」現金（B欄） | `shared` ＋ settled_on_spot=true（三人均分、無欠款）。 |
| 福岡檔「均付」刷卡（C欄，D=刷卡人） | `shared`、付款人＝刷卡人（產生欠款）。 |
| 福岡檔 E/F/G 金額不等的「各自分擔」列 | 依 Stage 0 對該列的判讀（各自分擔＝individual；由誰代墊依檔內線索），列入基準表讓 Rozi 一併確認。 |
| 福岡檔 K/L/M「刷自己卡自付」 | `personal`，台幣金額。 |

**幣別規則（Rozi 已拍板）**：
- 現金消費：照當地貨幣記 `foreign_amount`，並設定現金匯率（用 Excel 記載的當日匯率）；
- 刷卡消費：以台幣記 `twd_amount`；外幣金額若有，當純記錄填入，**不**為刷卡設定單一匯率（銀行匯率浮動）；
- `payment_method`：備註 💰→cash、💳→credit_card、WOWPASS/Linepay→stored_value、空白→credit_card。

**其他**：
- 贊助（濟州島「金主贊助 $50,000」）：**不謄入**（維持「忠實記實際消費、不含贊助」的既有決策）；Excel「每人平均」顯示值不在驗收範圍。
- Excel 待填/空白金額：照實留待填，不自己補數字。
- 小計、日期列、總計後的彙總列、KRW 分解註記列：一律跳過（依濟州島規則文件）。

## Stage 1–2：UI 自動化謄入（Playwright）

- 寫 Playwright 腳本，讀 fixture JSON，**逐筆走真實 UI** 記帳（這同時就是一輪線上實測 QA，UI 層的 bug 要記下來）。
- 四個新行程名稱一律加後綴「（Excel重謄）」，與既有正式行程區隔。
- 節奏：每趟先謄**第一天** → 立即比對該日小計 → 通過才全速謄整趟。任何一筆 UI 上找不到對應選項（toggle、幣別、成員…）→ 記入問題清單，跳過該筆並標記，不要硬塞近似值。
- 進度寫 `歷史資料匯入/checkpoint.json`（行程／已謄筆數／對應 expense 標識），中斷可續跑，**嚴禁重複謄同一筆**。

## Stage 3：驗證迴圈

- 驗證腳本以**唯讀**方式取 Tripay 數字（分享唯讀頁或 Supabase anon 讀取皆可），輸出每行程「Excel 基準 vs Tripay 實際」對照＋diff。
- 迴圈：謄入 → 驗證 → 列 diff → 定位原因（解析錯？謄入錯？產品 bug？）→ 修 → 再驗，直到 4×2 全綠。
- diff 屬**系統性產品 bug**（如進位規則、settled_on_spot 計算錯誤、統計卡幣別錯）時：**不准改資料遷就數字**，記入「產品問題清單」（含重現步驟）後回報；資料面正確且差額 ≤ ±1 視為通過。
