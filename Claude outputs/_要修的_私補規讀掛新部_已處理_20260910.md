## 補-1　把 Cowork 緊急套上去的修正補成 migration 檔（上一輪漏讀）

2026-09-10 中午新使用者註冊被擋（`Database error saving new user`）。
根因：`public.handle_new_user()` 是 `SECURITY DEFINER` 但**沒設 `search_path`**，
執行時沿用呼叫者（GoTrue 的 `supabase_auth_admin`，其 role 設定是 `search_path=auth`，
**沒有 public**）的設定，函式裡又寫無前綴的 `insert into profiles ...`
→ `relation "profiles" does not exist` → trigger 失敗。

**Cowork 已經直接對 production 套用了修正**（`apply_migration`，名稱
`fix_handle_new_user_search_path`），因為當下新使用者完全註冊不了。
**這段 SQL 沒有經過第二個人檢查，請覆核**：

```sql
create or replace function public.handle_new_user()
returns trigger language plpgsql security definer
set search_path = public, auth
as $function$
begin
  insert into public.profiles (id, google_sub, display_name, avatar_url)
  values (new.id, new.raw_user_meta_data->>'sub',
          new.raw_user_meta_data->>'full_name', new.raw_user_meta_data->>'avatar_url')
  on conflict (id) do nothing;
  return new;
end;
$function$;
```

另外 Cowork 盤點了 `public` schema 全部 6 個 `SECURITY DEFINER` 函式，
**`confirm_settlement` 有同一個地雷**（沒設 `search_path`）。它現在沒壞
（前端以 `authenticated` 呼叫，那條路的 search_path 含 public），但寫法一樣，
而且炸的是**結算**。

### 要做

1. `supabase/migrations/` 補一個 migration 檔，內容與上面那段完全一致
   （讓 repo 跟 production 對得起來）。**不要對 production 再跑一次**。
2. 同一個檔（或另一個檔）給 `confirm_settlement` 補上
   `set search_path = public, pg_temp`（跟其他四個一致），**函式主體一個字都不要動**。
   ⚠️ **不要自己對 production 下 DDL**，Cowork 複驗時套用。
3. 覆核意見寫進 `_停點.md`。

### 停止條件

- **補-1-1** 新增的 migration 檔內含 `set search_path = public, auth` 與 `public.profiles`
- **補-1-2** 也含 `confirm_settlement` 與 `set search_path = public, pg_temp`
- **補-1-3** `_停點.md` 貼出 `confirm_settlement` 改前改後的 diff，證明主體逐字相同
- **補-1-4** `_停點.md` 列出全部 6 個 `SECURITY DEFINER` 函式與各自的 search_path 狀態

## 讀-1　🔴 讀不到的時候，不准畫成「你還沒有資料」

Cowork 複驗時量到的**新缺口**（不是你上一輪做壞的，是 Cowork 的指令沒涵蓋）：

| 網址 | 畫面現在顯示 | 問題 |
|---|---|---|
| `?screen=s01&fail=read` | 「還沒有行程。第一趟要去哪？」 | 讀不到 → 被畫成「新使用者」 |
| `?screen=s03&fail=read` | 「消費紀錄 · 0 筆／第一筆從哪裡開始？」 | 讀不到 → 被畫成「這趟還沒記帳」 |

**這比登入那個更嚴重**：登入失敗只是沒說話，這個是**說了錯的話**。
使用者在收訊差的地方打開 App，會以為自己的帳不見了——
而「在國外、收訊差」正是 Tripay 的核心情境。

### 三題（交付前檢查第 7 條）

1. **什麼情境看到？** 旅遊中收訊差、或剛好斷線時打開 App。
2. **要幫使用者做什麼決定？** 分辨「我的資料沒了」還是「只是現在拿不到」；要不要重試。
3. **需要什麼資訊？** 「**資料還在**」這四個字。舊畫面完全沒回答，還誤導成相反的意思。

### 文案（Copywriter ＋ UX ＋ Aria 定稿，逐字照抄）

**行程列表讀不到**（取代「還沒有行程。第一趟要去哪？」那個空狀態）：

- 標題：`現在讀不到你的行程`
- 內文：`資料還在，只是連不上。等收訊回來再重新整理一次。`
- 按鈕：`重新整理`（按下去重新查一次，不是整頁 reload）

**行程頁讀不到消費**（取代「第一筆從哪裡開始？」那個空狀態）：

- 標題：`現在讀不到這趟的帳`
- 內文：`資料還在，只是連不上。等收訊回來再重新整理一次。`
- 按鈕：`重新整理`

⚠️ **「還沒有資料」的空狀態要保留**——那是真的沒資料時該顯示的東西。
這一節要做的是**分辨兩者**：查詢有錯誤 → 顯示讀不到；查詢成功但結果是空的 → 顯示原本的空狀態。

### 停止條件

- **讀-1-1** `?screen=s01&fail=read`：畫面出現「現在讀不到你的行程」與「資料還在」，
  且**不得**出現「還沒有行程」或「第一趟要去哪」（反向）
- **讀-1-2** `?screen=s03&fail=read`：畫面出現「現在讀不到這趟的帳」與「資料還在」，
  且**不得**出現「第一筆從哪裡開始」（反向）
- **讀-1-3** 反向：`?screen=s01`（不帶 fail、且真的沒行程的假資料）仍然顯示
  「還沒有行程」的原本空狀態，**不得**出現「讀不到」
- **讀-1-4** 兩頁的「重新整理」鈕有效可點區 `h ≥ 44`（C6）

## 掛-4　量測靶要能**執行期**切換失敗模式

`?fail=offline` 是載入時讀網址參數，所以「App 已經開著、然後網路斷了」這個
**真實世界唯一會發生的離線情境**在量測靶上走不到
（offline 連讀取都失敗 → 清單是空的 → 使用者根本點不到任何一筆去編輯）。
C12-3 因此只能 skip。

### 要做

`installStub.ts` 的 `failMode` 從常數改成每次呼叫時讀：
`window.__FAIL__` 有值就用它，沒有才用網址參數。不帶參數、也沒設 `__FAIL__` 時行為完全不變。

### 停止條件

- **掛-4-1** 正常載入 `?screen=s03`（樁正常）→ 執行期設 `window.__FAIL__='offline'`
  → 呼叫 `update` 回的 `error.message` 是 `Failed to fetch`
- **掛-4-2** 反向：把 `window.__FAIL__` 設回 `null` → 同樣的呼叫 `error` 是 null
