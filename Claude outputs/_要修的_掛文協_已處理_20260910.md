## 補-1　把 Cowork 緊急套上去的修正補成 migration 檔（覆核 ＋ 落檔）

### 發生什麼事

2026-09-10 中午，一位測試使用者（家人的 Gmail，不寫進版控；已在 Google 測試使用者白名單內）
登入時看到「登不進去 ／ Google 的回覆：**Database error saving new user**」。

**根因（Cowork 實測重現，不是讀碼推論）**：

`public.handle_new_user()` 是 `SECURITY DEFINER` 但 **`proconfig` 是 null——沒有設 `search_path`**，
所以執行時沿用**呼叫者**的 search_path。呼叫者是 GoTrue 的 `supabase_auth_admin`，
它的 role 設定是 `search_path=auth`（**沒有 public**）。
函式內寫的又是無前綴的 `insert into profiles (...)` → `relation "profiles" does not exist`
→ trigger 失敗 → GoTrue 回 `Database error saving new user`。

重現方式（唯讀，跑完 rollback）：

```sql
begin;
set local search_path = auth;          -- ← 關鍵：模擬 GoTrue 的環境
insert into auth.users (id, instance_id, aud, role, email, raw_user_meta_data, created_at, updated_at)
values (gen_random_uuid(), '00000000-0000-0000-0000-000000000000',
        'authenticated','authenticated','zz-probe@example.com',
        '{"sub":"zz","full_name":"ZZ"}'::jsonb, now(), now());
rollback;
```

⚠️ **Cowork 已經直接對 production 套用了修正**（`apply_migration`，名稱
`fix_handle_new_user_search_path`），因為新使用者完全註冊不了。
**這段 SQL 沒有經過第二個人檢查，請覆核。**

套上去的內容：

```sql
create or replace function public.handle_new_user()
returns trigger
language plpgsql
security definer
set search_path = public, auth
as $function$
begin
  insert into public.profiles (id, google_sub, display_name, avatar_url)
  values (new.id,
          new.raw_user_meta_data->>'sub',
          new.raw_user_meta_data->>'full_name',
          new.raw_user_meta_data->>'avatar_url')
  on conflict (id) do nothing;
  return new;
end;
$function$;
```

套用後實測：同樣的 `set local search_path = auth` 情境下，
`profiles` **有建立成功**（跑完 rollback，沒有留測試資料）。

## 規-1　補一條規則：寫入路徑實跑，要用**真正會執行它的身分與環境**

> 2. **search_path**（`set local search_path = …`，照 `pg_roles.rolconfig` 抄）
> 3. **JWT claims**（`set local request.jwt.claims = …`）
