## 🔴 修-2　離線存檔變成「靜默失敗」——這一輪改壞的（常設 C12 抓到）

### 症狀（Cowork 實測，不是讀碼推論）

量測靶 `?screen=s03`，載入後在**執行期**切 `window.__FAIL__ = 'offline'`
（模擬「App 已經開著、然後網路才斷」），點一筆消費打開編輯、改標題、按「記下來」：

- 表單**關掉了**
- 按鈕回到「記下來」
- **畫面上完全沒有任何訊息**（沒有「現在連不上網路」，也沒有「存不起來」）
- 但那筆其實**沒有存進去**

使用者會以為存好了。這比 Rozi 原本遇到的「卡在存檔中…」更糟——
卡住至少看得出來沒完成，靜默關閉會讓人以為成功。

### 三個對照，證明是這一輪改的

| 條件 | 結果 |
|---|---|
| **AF 之前的建置**（`dLG`，同一支腳本、同一個操作） | ✅ **有訊息** |
| 這一輪的建置（`dist-harness`，bundle `harness-D1EOjkzw.js`） | ❌ 沒有訊息 |
| 同一輪、改用 `?fail=write` | ✅ 有訊息（`verify_C12` 的 C12-1 是綠的） |

樁確實會失敗——直接呼叫 `__SUPABASE_STUB__.from('expenses').update(...)`
在兩種寫法（`?fail=offline` 與執行期 `window.__FAIL__='offline'`）下
都回 `{ error: { message: 'Failed to fetch' } }`。所以**不是樁沒壞**。

### 可能的方向（給你查，不是結論）

`fail=offline` 與 `fail=write` 的差別是**前者連 `select` 也失敗**。
`ExpenseFormSheet.tsx` 第 446 行 `mutationFn` 的第一件事是
`const { data: { user } } = await supabase.auth.getUser();`——
這一行在 offline 下的行為值得先看。另外 `guardedWrite`／`withWriteTimeout`
有沒有可能把 rejection 吞掉、讓 react-query 誤判成成功，也要一起看。

⚠️ **不要靠讀碼下結論**，用上面那個操作實走一次再說。

### 停止條件

1. 量測靶 `?screen=s03`，執行期切 `window.__FAIL__='offline'` 後編輯一筆消費按「記下來」：
   畫面上 **3 秒內**出現「現在連不上網路」
2. 同一個情境下，**表單不准關閉**，剛才輸入的值還在欄位裡
3. `?fail=write` 的行為不變（仍然顯示「存不起來，再試一次」）
4. `?fail=hang` 的行為不變（15 秒內按鈕回可按 ＋ 有訊息）
