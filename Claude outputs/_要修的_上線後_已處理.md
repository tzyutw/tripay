## ① 分享頁把「誰付給誰」重複列了 12 次（線上實測）

**現象**：開 `https://tzyutw.github.io/tripay/share/<token>`（2025 北海道四寶團），
「誰付給誰」底下同樣三筆（Ziyu→Ning $7,951、Mei→Ning $6,917、Xiu→Ning $3,015）
**一路重複**。實測那趟有 **12 筆結算**：10 筆 `superseded`、1 筆 `confirmed`、1 筆 `draft`，
每筆各 3 個 item，全部被畫出來 → 36 列。

**根因（一處）**：`src/pages/SharePage.tsx:69–70`
```ts
const tx = data.settlement_items.length
  ? data.settlement_items.map(i => ({ from: i.from_member_id, to: i.to_member_id, amount: i.amount }))
  : settleTrip(S, expenses, trip as never).tx;
```
`data.settlement_items` 是 **這趟全部結算的 item**，沒有挑「哪一次結算」。

**這是這一批做出來的退步，不是舊有問題**：改版前的 `SharePage.tsx`（`750d857^`）
第 85–88 行是 `.from('settlements').eq('status','confirmed').order('created_at',{ascending:false})`，
本來就有挑；重寫成走 RPC 之後那層篩選掉了。
`SettlementPage.tsx:83–84` **現在仍然有**（`.eq('status','confirmed')` ＋ 依 `created_at` 倒序），
所以兩頁行為不一致——分享頁要跟它一致。

**要做的（只改這一處）**：
先從 `data.settlements` 挑出**唯一該用的那一次**——
`status === 'confirmed'`，若不只一筆取 `settled_at` 最新的（`settled_at` 為 null 視為最舊）；
再只取 `settlement_id` 等於它的 items。
**挑不到 confirmed 就走原本的前端預覽** `settleTrip(...)`（維持「還沒結算就用前端預覽」的行為）。

不要動 `get_shared_trip()`、不要動 `SettlementPage`、不要動版面。

**停止條件**：
1. 新增測試：fixture 放 **3 筆結算**（1 superseded ＋ 1 confirmed ＋ 1 draft，各 3 個 item），
   分享頁只畫出 **confirmed 那 3 列**，且金額對得上。
2. 反向驗證：把篩選拿掉 → 這條**要紅**（斷言要比對列數，不能只看「有沒有出現某個字串」，
   否則重複時照樣通過）。
3. `npx tsc --noEmit` 零錯；`npx vitest run` 全綠且項數 **≥ 212**。
4. 已 commit **並 push**（這次不用等 `_可以推了.txt`，我會在上線後直接複驗；
   但 push 前 build 與測試必須都綠）。
